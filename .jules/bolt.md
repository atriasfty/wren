## 2025-02-18 - Avoid O(N) database queries and O(N) API calls before determining relevance
**Learning:** Found a major architectural bottleneck where the Discord message event handler executed an O(N) database query (`enforceBan`) for every single message received by a server, and an O(replies) Discord API message fetch to determine the author of replied messages before it even determined if the message was relevant (mentions the bot, or in a source channel).
**Action:** Always check the fastest and cheapest preconditions (like `directlyMentioned`, `isSourceChannel`, or using cached objects / checking `mentions.repliedUser`) first. Delay expensive database queries and API calls until you are confident the data needs to be acted upon.
## 2025-02-18 - Caching bans in tenantContext
**Learning:** `enforceBan` is checked very frequently, such as on every message creation. Before this optimization, it performed an asynchronous DB lookup `isBanned`. This led to high latency and database load. Caching the bans on the `tenantContext` (which is already aggressively cached) transforms this into an O(1) synchronous check. To avoid a stale cache when new bans are added or removed, it's necessary to invalidate the `tenantContext` dynamically by invoking `invalidateTenant`.
**Action:** Be mindful of frequent asynchronous calls in the message handling hot path. When an entity is already fetching a comprehensive object like `tenantCtx`, consider augmenting that object with related frequently accessed tabular data to convert subsequent O(N) database queries into O(1) memory queries, while making sure to add cache invalidation hooks in the respective mutation functions (e.g. `addBan` and `removeBan`).
